# Единая экосистема: панель + сайт + Discord-бот

Документ фиксирует, что у нас есть сейчас, что решено и в каком порядке делается.
Он рабочий: по нему продолжается работа, поэтому решения записаны с причинами.

## Что уже есть

| Часть | Стек | Объём | Состояние |
|---|---|---|---|
| **Панель** | Node.js, Express, без фреймворков на фронте | ~14 тыс. строк | карта, мод-мост, журнал событий, моды, аккаунты с правами, Discord OAuth |
| **Сайт** | Python, FastAPI + Jinja | ~3 тыс. строк | новости, лор, правила, профиль, админка контента, вход через Discord |
| **Бот** | Python, discord.py, 14 модулей | ~14 тыс. строк | верификация, торговец (3400 строк), тикеты, спавнер групп, админ-панель, CFTools |
| **База** | MySQL (XAMPP), PyMySQL | 14 таблиц | сайт и бот уже частично переехали; часть данных осталась в JSON |

## Решения

**Панель — ядро.** Сайт и бот остаются на Python: переписывать 14 тысяч строк
рабочего кода (торговец, тикеты, спавнер) на Node — недели работы и большой риск
без выгоды. Панель становится единым центром: аккаунты, права, верификация,
данные с игрового сервера, API. Сайт и бот ходят в неё по HTTP и читают ту же
базу.

**Одна база — MySQL на XAMPP.** Таблицы панели называются `panel_*`; чужие
(`user_profiles`, `site_*`, `trader_*`, `content_*`, `guild_settings`) панель не
меняет. База **необязательна**: пока `panel.database.enabled = false`, панель
работает на файлах, как раньше — обновление не должно ломать рабочую панель.

**Дизайн — панельный.** Страницы сайта постепенно переводятся на оформление
панели; вход у сайта и панели становится общим.

## Почему верификация сейчас работает неверно

Разобрано по `bot/modules/verification.py` (2046 строк):

1. **Владение Steam не доказывается.** `VerificationModal` просит игрока
   *вписать руками* ссылку на профиль и ник. Можно указать чужой профиль —
   проверяется только то, что такой профиль существует и не занят.
2. **Истина в трёх местах.** `data["verified_players"]`, `data["steam_links"]`
   (JSON) и `user_profiles` (MySQL). Код читает все три с подстраховками
   (`effective_linked_discord_id`), поэтому источники расходятся — отсюда
   «то работает, то нет».
3. **Каждая заявка ждёт админа**, ник свободный, фракция сверяется с
   `GroupSpawner.json` с диска.

## Как будет работать верификация

Решено: **автоматически, по доказанному входу**, без очереди к админу.

```
Discord: игрок жмёт кнопку в канале верификации
   -> бот просит у панели ссылку:  POST /api/verify/start {discordId, discordTag, guildId}
   -> панель отдаёт одноразовую ссылку (токен, живёт 15 минут)
Браузер игрока:
   -> вход через Discord (OAuth2) — панель убеждается, что это тот же человек
   -> вход через Steam (OpenID)   — Steam сам подтверждает владение аккаунтом
   -> панель пишет связку в panel_identity и закрывает сессию верификации
Бот:
   -> получает событие (или спрашивает GET /api/verify/status?discordId=…)
   -> выдаёт роли, ставит ник, при необходимости добавляет во фракцию
```

Что это меняет: подделать нельзя — Steam OpenID подтверждает владение
криптографически, а Discord OAuth подтверждает, что кнопку нажал именно этот
аккаунт. Ник берётся из Steam, а не из поля ввода. Истина одна — `panel_identity`.

## Таблицы панели (сделано)

| Таблица | Зачем |
|---|---|
| `panel_identity` | доказанная связка Discord ↔ Steam: `discord_id` (ключ), `steam_id` (уникальный), ник, когда и чем подтверждено |
| `panel_verify_sessions` | незавершённые верификации: токен, этап, срок |
| `panel_audit` | кто что сделал через панель — общий журнал для сайта и бота |

## Что нужно от владельца

1. **Перевыпустить секреты.** В присланном архиве лежали настоящие `.env`:
   токен Discord-бота, ключ Steam API, секрет CFTools, пароль MySQL. Архив
   прошёл через переписку — считайте их раскрытыми.
2. **Ключ Steam Web API** — для проверки OpenID и получения ника: нужен тот же,
   что уже используется ботом.
3. **Адрес панели, видимый игрокам** — он попадёт в ссылку верификации и в
   Redirect URI приложения Discord.
